Django Channels + Redis is the right choice. SSE is only needed for one-way pushes (like slot updates on the booking page). WebSocket handles chat fully.
Chat room lifecycle
1Payment confirmed → Booking status = confirmed
2Signal auto-creates ChatRoom linked to Booking (is_active=True)
3Both user and owner can connect via WS using their JWT token
4One-shot Celery task scheduled at booking creation with eta=booking.end_time → sets is_active=False
5Consumer sends system message "Room closed" then closes WS connection
6Messages retained in DB for dispute resolution, not shown in UI
Avoid Celery beat periodic polling. Schedule one-shot tasks with exact eta=booking.end_time per booking. If worker restarts, tasks are persisted in Redis and will execute at the correct time.

SSE — when to use it
Use SSE for
Real-time slot availability updates on the booking page — push slot status changes to all viewers without them opening a WebSocket. Also useful for owner dashboard live stats.
Use WebSocket for
Chat rooms (bidirectional). Both owner and client send messages. WS is mandatory here. Also consider for match join notifications.
Slot blocking strategy
When a user starts booking, create a pending Booking with a 10-minute expiry (use Celery). Lock the slot via DB constraint. If payment isn't completed in 10 min, Celery cancels the booking and releases the slot. This prevents double-booking during checkout.
Booking.objects.create(status="pending", ...)
release_pending_booking.apply_async(args=[booking.id], countdown=600)
Request flow
HTTP requests→Nginx (reverse proxy)→Gunicorn + Django→DRF Views → PostgreSQL
WebSocket→Nginx (ws:// upgrade)→Daphne (ASGI)→Channels Consumer → Redis
Background jobs→Celery Workers→Redis (broker)→DB / Email / Push
Scheduled tasks→Celery Beat (prune expired tokens)+One-shot tasks (eta) per booking for room closure, slot release, reminders
Service layers
Django apps (modules)
users · turfs · bookings · payments · chat · matches · reviews · notifications · dashboard — each as a separate Django app. Keeps code isolated and testable.
Authentication
djangorestframework-simplejwt for JWT. Short-lived access tokens (15 min), long-lived refresh (7 days). Blacklist refresh token in BlacklistedToken model on logout.
Image storage
django-storages + Cloudinary or S3. Never store images on server disk. Generate thumbnails on upload. Serve via CDN URL.
Permission classes
IsOwner, IsClient, IsBookingParticipant (for chat), IsBookingOwner (for review). Role-based from User.role field.
Celery tasks
release_pending_booking · close_expired_rooms (one-shot per booking) · send_booking_reminder · update_avg_rating · send_push_notification · prune_blacklisted_tokens
Caching strategy
Cache turf listings (short TTL ~2 min). Cache slot availability per turf per date. Invalidate cache immediately on booking creation + cancellation. Use Redis.

Read replicas (later)
Route analytics, dashboard, and listing queries to a read replica. Writes (booking, payment) go to primary only. Django supports this via DATABASE_ROUTERS.
API design for scale
Pagination
Use cursor-based pagination (not offset) for messages and bookings. Offset pagination breaks under concurrent inserts.
select_related / prefetch
Always use select_related and prefetch_related in viewsets to avoid N+1 queries. Use django-debug-toolbar in dev to catch them.
Rate limiting
DRF throttling on auth endpoints. Use django-ratelimit or nginx rate limiting for booking and payment endpoints.
Idempotency
Payment endpoints must be idempotent. Use idempotency keys (UUID from client via X-Idempotency-Key header) to prevent double charges on retry.
Future scaling path
Phase 1 (MVP)Single server, all services co-located. Docker Compose.
Phase 2 (growth)Separate Daphne (WS) from Gunicorn (HTTP). Add Redis cluster. RDS for PostgreSQL. S3 for media.
Phase 3 (scale)Multiple Gunicorn instances behind load balancer. Celery worker pool. CDN for assets. Read replicas.
Phase 4 (enterprise)Extract chat and notifications as separate services. Kubernetes. Elasticsearch for match/turf search.
